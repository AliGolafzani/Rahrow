# AUTH-01: Auth, User, RBAC and Audit foundation

This is the bounded first product schema, based on the approved PRD v1.0 (2026-09-27), approved AUTH-01 plan and 2026-10-03 refinements. It supplies internal foundations only. There are no authentication, registration, profile-edit, permission-management or admin endpoints; the web application remains unchanged.

## Requirement-to-schema map

P = product-defined requirement. T = implementation-owned representation/security necessity. All UUIDs are generated by Prisma; they introduce no sequences. Times use UTC-capable PostgreSQL timestamptz; birthDate is date-only.

| Model | Product requirement and fields | Technical fields and constraints |
| --- | --- | --- |
| User | P: id, required mobile, email, firstName, lastName, birthDate, displayName, avatar (PRD §§6,14) | T: UUID primary key, unique canonical mobile, bounded strings, createdAt/updatedAt. Nullable profile storage settles no onboarding gate. Email has no invented uniqueness rule. No status column. |
| Role | P: role definition (§§3,14) | T: UUID id, unique key, createdAt/updatedAt |
| Permission | P: capability definition (§§3,14) | T: UUID id, unique key, createdAt/updatedAt, exact non-wildcard capability syntax |
| UserRole | P: user-role assignment (§14) | T: composite key, foreign keys, createdAt, roleId lookup index |
| RolePermission | P: role-capability assignment (§14) | T: composite key, foreign keys, createdAt, permissionId lookup index |
| AdminCredential | P support: mandatory Password + TOTP (§§3,12) | T: userId primary/foreign key, passwordHash, totpCiphertext/Nonce/AuthenticationTag/KeyVersion, lastAcceptedTotpStep, createdAt/updatedAt; authenticated-encryption envelope size/replay constraints |
| AuthSession | P support: secure rotation/revocation/logout (§12) | T: UUID id/userId, unique tokenDigest, immutable-by-interface authenticationMethod, createdAt/expiresAt/revokedAt, unique rotatedFromId self-reference, expiry/user index and valid chronology |
| OtpChallenge | P support: mobile OTP expiry/attempt/abuse controls (§§6,12) | T: UUID id, targetDigest, codeMac, createdAt/expiresAt, failedAttempts/attemptLimit, consumedAt, target-expiry index and bounded state checks |
| AuthRateLimitBucket | P support: atomic Auth/OTP rate limits (§§6,12) | T: composite bucketKey/scope/windowStart key, count/expiresAt, expiry index; keyed identifiers only, explicit bounded scopes |
| AuditLog | P: actor, action, target, before/after summary, occurredAt (§§3,12,14) | T: UUID id, nullable actorId FK for generic future events, bounded action/entityType/entityId, optional correlationId, bounded JSON objects, actor/entity time indexes |

Only these ten tables and Prisma's `_prisma_migrations` bookkeeping are allowed. Technical `AuthenticationMethod` enum values express evidence, not product roles or account status. FK deletes are restrictive; account deletion policy is not invented. Product defaults, production grants, role matrix and privileged bootstrap seeds are absent. There is no product seed.

## Boundaries and contracts

- Database owns a lazy Prisma client and shutdown cleanup. Module import/startup neither opens a database connection nor runs migrations.
- Users owns private account persistence. Its public query selects only displayName/avatar, then uses an explicit projection. PublicProfile is a type-only shared contract; importing the shared package at runtime still has no exports. No mobile/email/birthDate/id or private name fields are returned publicly, and no display-name fallback is invented.
- Auth owns security-state persistence and primitives. AuthService derives principals only from a validated opaque token and a current nonexpired/unrevoked persisted mobile session. No request.user or role claims are trusted. Roles changing cannot upgrade the authenticationMethod.
- RBAC resolves current capability assignments in PostgreSQL. RequireCapability takes exactly one key; missing requirements/identity/assignment fail closed. No wildcard, role shortcut, implicit super-admin or multiple-capability AND/OR semantics exists. The guard's bearer parsing is an isolated internal test boundary, not a published transport/login contract. CapabilitiesGuard checks identity plus capability only: it is insufficient for a future admin-sensitive operation requiring Password + TOTP, whose boundary must independently require verified admin assurance.
- Audit owns a bounded append-only interface. Current exercised summaries contain only an assigned boolean. User-role assignment and its actor/action/entity/time audit record commit in the same transaction. The two exercised assignment/removal action identifiers are a limited foundation vocabulary, not an exhaustive product event catalog. No removal workflow exists yet.

User-role assignment persistence is internal and not exported as a management endpoint. A future authorized use-case must perform capability and required authentication-assurance checks before invoking persistence; AUTH-01 does not choose who may manage permissions.

## Security mechanics

Admin password primitives use async scrypt N=131072, r=8, p=1, 256 MiB maxmem, 16-byte random salts and versioned bounded encodings. Stored parameter tampering cannot select more expensive work. No ordinary-user password exists. Production concurrency/rate admission for password verification is deferred with the admin login boundary.

OTP primitives use six CSPRNG decimal digits, a keyed target digest, and a challenge-id/target-bound verification MAC. HKDF purpose keys and message domains separately protect target, code, rate-limit identifiers and TOTP encryption. All persisted digests are lowercase hex64. OTP codes are never persisted. The foundation recommended defaults are five minutes/five attempts; storage supports bounded attempts (1–20), with no complete issuance/delivery orchestration. Consumption locks the challenge row, checks current time after acquiring the lock, atomically increments failures, rejects expired/exhausted/consumed/mismatched challenges, and permits only one winner. Session rotation likewise checks time after locking; session lookup and rate-limit admission recheck expiry after database waits.

AES-256-GCM uses fresh 12-byte nonces, 16-byte tags, user/version-bound authenticated context, and injected external 32-byte root keys. keyVersion is only a lookup identifier. Envelope strings are canonical base64url at the crypto boundary; persistence uses bytea. Missing keys, unknown versions, context mismatch and tampering fail closed. Decryption callers must clear returned plaintext buffers after use. Tests generate keys at runtime; neither production secrets nor production-like fixture keys are committed.

TOTP replay persistence uses an atomic monotonically increasing counter. Advancing that counter is only storage coordination: it does not verify RFC TOTP or represent admin authentication. AUTH-01 exposes no session-issuance API. Admin session resolution/rotation is intentionally unavailable, even if an AdminCredential or ADMIN_PASSWORD_TOTP fixture record exists. AUTH-02 must verify both password and actual TOTP before adding any success/issuance path.

Session tokens contain 32 random bytes, are never stored, and are represented by domain-separated SHA-256 digests. Primitive token objects omit the raw bearer from normal JSON/inspection. Rotation revokes the prior record and inserts one successor transactionally, preserving mobile assurance and absolute expiry. Revocation is idempotent. Cookies/CSRF, login, issuance, admin enrollment/recovery and RFC TOTP verification remain deferred.

Rate limits use PostgreSQL insert/on-conflict updates with exact keyed scope/window identity. A bounded counter cannot admit more than the configured limit under concurrency. Stable window derivation and calling the limiter from every future auth boundary remain orchestration responsibilities; callers cannot choose user-controlled limit/window settings in a future endpoint.

## Migration and verification

Migration: `20261003195100_auth_domain_foundation`. It was generated from the empty approved baseline and augmented with reviewed technical CHECK constraints. `prisma migrate deploy` is the only deployment path; no `db push`, automatic startup migration or manual production mutation.

Local empty baseline / fresh cluster:

1. Follow the guarded local infrastructure guide; prove the selected QA resources are new and disposable.
2. Run `npm run db:check:empty` (read-only empty-catalog preflight).
3. Run `npm run db:migrate` then `npm run db:check`.
4. Re-run migrate deploy; verify the migration history/checksum and schema remain unchanged.
5. Normal down/up must retain exact volume creation time and PostgreSQL cluster identity; rerun schema checks.
6. Use only the documented scoped, explicitly confirmed cleanup.

CI independently covers direct-fresh and retained-empty Foundation migration paths: after the first path completes, only its proven-owned disposable namespace is reset, and a separate empty cluster is retained across down/up before migration. CI additionally compares full relation/column/constraint/index/migration snapshots across replay and restart and executes actual PostgreSQL negative/concurrency tests through compiled repository methods. The write-test runner refuses without GitHub CI identity, exact isolated project syntax and the disposable-test opt-in. Fixture rows are never production seeds, and the complete isolated volume is removed by existing always-cleanup logic. A Docker-less environment can run offline tests but cannot claim these live acceptance gates.

Recovery: for disposable local data, confirmed scoped reset followed by fresh versioned migrate deploy. For valuable/staging/production data, stop and use a reviewed forward repair plus separately approved backup/recovery plan. No speculative destructive down migration is provided. Applied migration files are immutable; future corrections require new versioned migrations.

## Dependency/build mechanics

Prisma client 7.10.0, PostgreSQL adapter 7.10.0 and driver pg 8.23.1 are runtime dependencies. The same Prisma 7.10.0 CLI tarball is a development-only npm alias, `prisma-cli: npm:prisma@7.10.0`; prisma.config.ts imports prisma-cli/config and existing prisma CLI commands remain unchanged. This prevents the client's optional package named prisma peer from inadvertently retaining development CLI dependencies in production. It changes placement, not package versions or advisory content. Full audit findings remain visible; runtime audit remains the unchanged zero-finding gate. TypeScript may still be retained through the client's optional peer; no claim that every type/build package disappears is made.

Generated code is ignored at src/generated/prisma. TypeScript rewriteRelativeImportExtensions compiles generated .ts imports to executable .js, while Node 24 native tooling can read source .ts directly. Both paths are verified. API build/typecheck and predev explicitly build shared contract declarations and generate Prisma first, so a clean checkout has no hidden dependency on a previous aggregate build. No generated Prisma code is committed.

## Product questions and deferred work

OQ-07 (email UX), OQ-14A (capability/profile gates), and OQ-14D (status meanings/transitions/access effects) remain OPEN. PRD requires a status concept eventually; its column/lifecycle is intentionally absent until Ali decides. No country parsing, phone eligibility, age restriction, default display name, administrator login identifier or recovery authority is invented.

AUTH-02 or later owns complete OTP/SMS/login orchestration, auth endpoints, session issuance/transport, RFC TOTP/login/enrollment/recovery, profile UX, final permission matrix and status behavior. All business modules, frontend auth and staging/production actions remain outside AUTH-01.
